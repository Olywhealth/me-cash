# meCash — Cross-Currency Transfer API

A Spring Boot service that lets users sign up, log in, and transfer money between accounts
**regardless of currency**, with automatic FX conversion. Built with Java 17, Spring Boot 3.5,
Spring Security (stateless JWT), Spring Data JPA, and BigDecimal money handling throughout.

## Quick start

Requires a JDK (17+). The app runs against an in-memory **H2** database by default, so no
external services are needed.

```bash
./mvnw spring-boot:run
# API is now on http://localhost:8080
```

End-to-end walkthrough with `curl`:

```bash
# 1. Sign up — an account with a random number, random currency (A or B) and a 1000.00
#    opening balance is created automatically.
curl -s -X POST http://localhost:8080/api/v1/auth/signup \
  -H 'Content-Type: application/json' \
  -d '{"email":"demo@mecash.io","password":"supersecret"}'
# => {"email":"demo@mecash.io","account":{"accountNumber":"8997688782","currency":"A","balance":1000.00,...}}

# 2. Log in — returns a bearer JWT.
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"demo@mecash.io","password":"supersecret"}' | jq -r .accessToken)

# 3. Transfer 100 (in the sender's currency) to a pre-existing account.
#    8997688782 is currency A; 6574839201 is currency B, so 100 A -> 134.55 B.
curl -s -X POST http://localhost:8080/api/v1/transfers \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"sourceAccountNumber":"8997688782","destinationAccountNumber":"6574839201","amount":"100.00"}'

# 4. Check balance and history.
curl -s http://localhost:8080/api/v1/accounts/8997688782/balance      -H "Authorization: Bearer $TOKEN"
curl -s http://localhost:8080/api/v1/accounts/8997688782/transactions -H "Authorization: Bearer $TOKEN"
```

Run the tests:

```bash
./mvnw test
```

## Architecture

Layered packages under `com.mecash`, grouped by responsibility — controllers, services, and
DTOs (`model`) each live in their own top-level package:

```
com.mecash
├── controller/                 All REST controllers (thin web layer)
│   ├── AuthController
│   ├── TransferController
│   └── AccountController
├── service/                    All business logic, one sub-package per service
│   ├── auth/        AuthService                 (sign-up + login)
│   ├── transfer/    TransferService             (atomic, locked, cross-currency core)
│   ├── account/     AccountService, AccountNumberGenerator
│   └── exchange/    ExchangeRateService, ConversionResult
├── model/                      All DTOs, by feature then request/response
│   ├── auth/request/     SignupRequest, LoginRequest
│   ├── auth/response/    AuthResponse, SignupResponse
│   ├── transfer/request/ TransferRequest
│   ├── account/response/ AccountResponse, BalanceResponse
│   ├── transaction/response/ TransactionResponse
│   └── common/response/  ApiError, PagedResponse
├── accountUser/ account/ transaction/ JPA entities + repositories (+ enums)
├── security/                   JWT issue/verify, auth filter, UserDetailsService, 401 entry point
├── config/                     Security config, OpenAPI/Swagger, typed properties, JPA auditing, data seeding
└── common/                     Currency enum, typed exceptions + global handler
```

Flow: **controller → service → repository**; controllers do validation + mapping, services own
the business rules and transaction boundaries, and all request/response shapes live in `model`.

## API docs (Swagger UI)

Interactive OpenAPI 3 docs are generated by **SpringDoc** and served with the app (no auth
required to view them):

| Resource   | URL                                          |
|------------|----------------------------------------------|
| Swagger UI | `http://localhost:8080/swagger-ui.html`      |
| OpenAPI spec (JSON) | `http://localhost:8080/v3/api-docs` |

To call the secured endpoints from the UI:

1. Expand `POST /api/v1/auth/login`, **Try it out**, and send valid credentials.
2. Copy the `accessToken` from the response.
3. Click **Authorize** (top right), paste the token (no `Bearer ` prefix), and **Authorize**.

All subsequent requests carry the bearer JWT. The scheme is defined in `config/OpenApiConfig`,
and the doc paths are whitelisted in `config/SecurityConfig`.

## API reference

All responses are JSON. Errors share one envelope:
`{ timestamp, status, error, message, path, fieldErrors? }`.

| Method | Path                                          | Auth   | Description                                   |
|--------|-----------------------------------------------|--------|-----------------------------------------------|
| POST   | `/api/v1/auth/signup`                         | —      | Register; auto-opens an account               |
| POST   | `/api/v1/auth/login`                          | —      | Authenticate; returns a JWT                   |
| POST   | `/api/v1/transfers`                           | Bearer | Transfer money (cross-currency aware)         |
| GET    | `/api/v1/accounts/me`                         | Bearer | List the caller's accounts                    |
| GET    | `/api/v1/accounts/{accountNumber}/balance`    | Bearer | Balance of one of the caller's accounts       |
| GET    | `/api/v1/accounts/{accountNumber}/transactions` | Bearer | Paged transaction history (money in & out)  |

### Status codes
| Code | When                                                                 |
|------|----------------------------------------------------------------------|
| 201  | Sign-up / transfer created                                           |
| 200  | Login / reads                                                       |
| 400  | Validation failure (bad email, non-positive amount, …)              |
| 401  | Missing/invalid token, or wrong login credentials                   |
| 403  | Accessing or transferring from an account you don't own             |
| 404  | Account not found                                                   |
| 409  | Email already registered                                            |
| 422  | Insufficient funds                                                  |

## Design decisions & assumptions

- **Email is the username.** The brief says sign up with email and log in with "username".
  The email serves as the unique username; there is no separate username field.

- **New accounts get a non-zero opening balance (default `1000.00`).** This is the key
  decision: the only pre-funded accounts in the brief (`1234567890` / `6574839201`) have no
  owner and cannot log in, so if new accounts started at zero **no accountUser could ever initiate a
  transfer**. New users are funded so requirement #3 is demonstrable. Configurable via
  `mecash.account.opening-balance`.

- **Currency is randomly assigned at sign-up** (A or B), as required.

- **Account numbers are 10-digit Strings**, generated randomly and checked for uniqueness
  against all persisted accounts (including the two seeded ones) — never stored as integers,
  so leading-zero / arithmetic bugs can't occur.

- **The two pre-existing accounts are seeded idempotently on startup** (`DataSeeder`) with no
  owner; they exist purely as valid transfer destinations.

- **The transfer `amount` is denominated in the source account's currency.** meCash converts
  it to the destination currency and credits the converted amount. The exact rate applied,
  source amount, and destination amount are all persisted on the transaction for audit.

- **Transactions are immutable audit records.** History is bidirectional: an account sees both
  money it sent (`DEBIT`) and money it received (`CREDIT`).

- **PostgreSQL is fully supported** (driver + profile included); H2 is the zero-setup default.

## Money & exchange rate

- All monetary values use `BigDecimal` (JPA `NUMERIC(19,2)`); rates are `NUMERIC(19,6)`.
- Reference rate (configurable): **A → B = 1.3455**.
  - `A → B`: `amount × 1.3455`
  - `B → A`: `amount ÷ 1.3455`
  - same currency: rate `1`, no conversion
- **Rounding policy, applied consistently:** amounts to scale 2 using `HALF_EVEN` (banker's
  rounding); rates to scale 6. Division is done at full precision and rounded exactly once.

Examples: `100.00 A → 134.55 B`; `100.00 B → 74.32 A`.

## Concurrency & correctness

Transfers are the one place money can be lost or duplicated, so:

- The whole transfer runs in **one transaction** — both balances change and the audit row is
  written atomically, or nothing happens.
- Both accounts are loaded under a **pessimistic write lock** (`SELECT … FOR UPDATE`), acquired
  in a **deterministic order (sorted by account number)** to serialise concurrent transfers on
  the same accounts and avoid deadlocks. An optimistic `@Version` column is a second guard.
- The balance check and debit happen while the lock is held, so an account **cannot be
  overdrawn** under concurrency. This is covered by an explicit concurrency test (10 parallel
  transfers; exactly the affordable number succeed, balance never goes negative).

Guard rails: positive-amount validation, self-transfer rejection, ownership enforcement on the
source account, and existence checks on both accounts.

## Testing

`./mvnw test` runs 21 tests:

- **`ExchangeRateServiceTest`** — A→B, B→A, same-currency, and rounding, asserted with
  `isEqualByComparingTo` (scale-safe BigDecimal comparison).
- **`AccountNumberGeneratorTest`** — 10-digit format and collision-retry.
- **`TransferServiceIntegrationTest`** — both FX directions, same-currency, insufficient funds
  (balances untouched), self-transfer, missing destination, ownership, and a **concurrency**
  test proving no overdraw.
- **`AuthAndTransferApiIntegrationTest`** — full HTTP journey through the real security filter
  chain (sign up → log in → transfer → balance → history) plus unauthorized, duplicate email,
  wrong password, invalid email, and cross-accountUser access denial.

## Configuration

Bound from the `mecash.*` namespace (see `application.properties`):

| Property                        | Default      | Meaning                                      |
|---------------------------------|--------------|----------------------------------------------|
| `mecash.jwt.secret`             | dev secret   | HMAC signing secret — **override in prod**   |
| `mecash.jwt.expiration-ms`      | `86400000`   | Token lifetime (24h)                         |
| `mecash.account.opening-balance`| `1000.00`    | Balance credited to a new account            |
| `mecash.exchange.rate-a-to-b`   | `1.3455`     | Units of B per unit of A                     |

### Running on PostgreSQL

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=postgres
# configurable via DB_URL / DB_USERNAME / DB_PASSWORD (see application-postgres.properties)
```
